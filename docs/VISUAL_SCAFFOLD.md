# Visual scaffold — what's built, what's yours

This branch contains **only the visual layer** of Project 5. Every mechanic in
the GDD is left as an empty, documented stub for its owner. Nothing here
decides how the game plays.

Read this before you start on your mechanic.

---

## The one-minute version

```
pipeline/     Blender scripts that RENDER the art. Re-runnable.
assets/       The rendered PNGs + the TileSet. Generated — don't hand-edit.
scenes/       Godot scenes, generated by pipeline/make_scenes.py.
scripts/      GDD architecture, one file per box. Stubs with TODO(owner).
docs/         This file.
```

Open `project.godot` in **Godot 4.4+**. It runs: you get a room, a HUD, a
player sprite that faces the mouse. Nothing moves yet, because movement is a
mechanic and mechanics are not mine to write.

## How to read a stub

Every script follows the same shape:

```gdscript
## GDD architecture box: what the diagram says this holds
## Reads: which scripts, and for what
## WHAT IS BUILT: ...
## WHAT IS NOT: ...

const GRAZE_DISTANCE_PX: float = 20.0   ## the GDD line it came from

signal meter_changed(value, max_value)  ## already wired to the HUD

func _physics_process(delta):
    # TODO(Daryl): the actual mechanic
    pass
```

Three rules I stuck to, so you can rely on them:

1. **Every GDD number is a named constant.** No magic numbers anywhere. If a
   number is wrong, change it in one place.
2. **Cross-script links are already wired.** Where the GDD says one script
   reads another, the signal connection exists and works. You fill in the
   body, not the plumbing. Example: `Player.took_damage` → `GrazeMeter`
   already subtracts 25.
3. **Visual feedback is already written.** Graze sparks, the Shockwave ring at
   exactly 150 px, the barrel blast ring at exactly 96 px, damage flashes,
   death fades, door lock states, cover damage stages. Call them; don't
   rebuild them.

## The art pipeline

The GDD's pipeline, implemented:

> model and texture in Blender → render with an orthographic camera at a fixed
> 3/4 angle, key light from the top-left → 8-direction sprite sheets → Godot
> AnimatedSprite2D

```bash
./pipeline/render_all.sh        # renders everything, ~10 min
python3 pipeline/check_anchor.py # measures it against the anchor asset
```

| File | What it makes |
|---|---|
| `rig_common.py` | The shared rig. Camera, lights, cel shader, ink outlines, palette. **Everything** goes through this. |
| `player.py` | The anchor asset. 8 directions. |
| `enemy.py` | Standard / elite / boss, 8 directions each. |
| `props.py` | Bullets, barrel, cover (3 damage stages), trap (armed/disarmed). |
| `tiles.py` | Floor variants, wall, door locked/open. |
| `check_anchor.py` | Measures any sprite: frame size, content bbox, palette drift. |
| `make_scenes.py` | Regenerates `scenes/*.tscn` from the sprites. |

**If you change `rig_common.py`, re-render everything.** A mixed set — half the
assets at one camera angle, half at another — looks worse than an unfinished
one.

### The anchor asset

> The player character's idle sprite, facing down-right, about 64 px tall in a
> 128 × 128 frame. Every other asset is checked against it.

Built, and the check is a command rather than an eyeball:

```
$ python3 pipeline/check_anchor.py assets/sprites/player/player_idle_SE.png
  frame      128 x 128
  content    x 47-91  y 9-73   (45 x 65 px)
  height     65 px   target 64 +/- 6
  OK         within anchor tolerance
```

It also reports palette drift, scoring each colour against the swatch ramps
rather than the flat swatches, because cel shading is *supposed* to produce
colours that aren't exactly on a swatch.

## Decisions I made that the GDD didn't cover

Flagging these because they're mine, not the GDD's, and you may want to
overrule them.

**1. Enemies are Blood Rust.** The palette table assigns swatches to floors,
walls, bullets and UI — but not to enemy bodies. Crypt Stone is the floor, so a
Crypt Stone enemy standing on the floor nearly vanishes (I rendered it; it came
out a black smudge). Stone Light is walls and cover, same problem. Blood Rust
is the only swatch not used by a large surface, it isn't Ember (the player's
accent) and it isn't Hostile Magenta. It also reads correctly: red is the thing
that hurts you.

**2. Camera elevation is 45°, not steeper.** "Fixed 3/4 top-down" doesn't give
a number. At 55° every character rendered as a bell shape, because vertical
foreshortening at 55° is `cos(55°) = 0.57` — a model loses nearly half its
height before the silhouette is drawn. 45° gives 0.71 and still shows plenty of
floor, which matters for reading bullet positions.

**3. Floor tiles are rendered straight down, not at 3/4.** Walls use the 3/4
rig. A floor quad seen at 45° can't tile against its neighbour without seams,
and a square room would need rhombus tiles. Every top-down game that renders
props at 3/4 does this.

**4. "1 m = 32 px" and the sprite scale are different things.** The GDD's
`1 m = 32 px` is a *gameplay-space* rule — barrel radius 3 m = 96 px, and so
on. It is not a claim about the projection. Sprite scale is set separately so
the anchor lands at 64 px. Both numbers are right; they live in different
spaces.

**5. `GameManager` is not literally an autoload.** The diagram says
"Main.tscn, autoload", but in Godot a script can't be both a scene root's
script and an autoload singleton. It lives on `Main.tscn`'s root (which is the
main scene, so it's always present) and exposes `static var instance`, so any
script can reach it as `GameManager.instance`. Only `CombatRewards` and
`Palette` are true autoloads.

**6. `Palette.gd` is new.** Not in the architecture diagram. It's an autoload
holding the palette as named constants so no hex is ever retyped, plus
`check_no_magenta()` — a debug-only guard that walks a scene and warns if
anything except an enemy bullet is magenta. The GDD calls that rule "one rule
above the rest", so it seemed worth enforcing in code rather than in review.

**7. Cover has three damage stages.** The GDD says cover "breaks after 5 hits"
but doesn't say the player can see the damage. They need to: the GDD also says
"the player can trade cover for a Shockwave", and you can't make that trade
without knowing how close the cover is to breaking. Intact (0–1), cracked
(2–3), crumbling (4–5).

**8. Traps have armed/disarmed art.** Same reasoning. The 2 s re-arm window is
something the player reads off the floor mid-fight, and Jarman's enemies
"steer clear of active hazards within 75 px" — so which traps are live changes
where enemies will walk.

1. **Who draws the anchor asset?** The GDD leaves this open. I've rendered a
   *working* one — a hooded figure — so nothing is blocked, but it's a

   marked proposed. It's the number that decides whether a 20 px graze window
   is a real decision or a reflex test, so it's worth playtesting early.

## What I did not do

- No mechanic logic. Not movement, not shooting, not waves, not pathing.
- **Nothing has been run in Godot.** There's no Godot binary on the machine I
  built this on. The `.tscn` files are generated to Godot 4 `format=3` and the
  GDScript is written against the 4.x API, but the first person to open the
  project should expect to fix import paths or a node-path typo. That's a
  five-minute job, not a rebuild — but I'd rather flag it than let you find it.
- Only 1 of the 10 room layouts. `Room.tscn` is layout #1 and the template for
  the other nine: duplicate it, move the markers, change the walls.
- No boss model beyond a scaled-up elite with a spike crown. The boss fight is
  due Dec 2.
- No audio, no music, no menus.
