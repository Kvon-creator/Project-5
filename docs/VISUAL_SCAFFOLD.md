# Visual scaffold — what's built, what's yours

This branch contains **only the visual layer** of Project 5. Every mechanic in
the GDD is left as an empty, documented stub for its owner. Nothing here
decides how the game plays.

Read this before you start on your mechanic.

---

## Update, 13 Nov: Enemy Adaptation, per the GDD (branch `backup-game`)

The three Dec 2 rules are in `Enemy.gd` and `RoomManager.gd`:

- **Pathing.** `RoomManager.bake_navigation()` bakes a `NavigationPolygon`
  from the room's floor outline minus every intact tome stack, every barrel
  and every *armed* trap (grown to the 75 px clearance), and rebakes when
  one breaks, blows up, or arms/disarms. An enemy with an obstacle or
  hazard within `OBSTACLE_DETECTION_PX` (200) follows the agent's path;
  otherwise a straight line is the path.
- **Hazard avoidance.** Armed traps are routed around by the mesh, and
  `_hazard_repulsion` is the safety net inside 75 px, turning sideways when
  the plate is dead ahead so the enemy does not stall. Knockback is not
  steered - that is how the player pushes an enemy onto a trap.
- **Ranged positioning.** `_cover_point` puts a hare or the scribe just
  behind a tome stack that sits about a band-width from the player; with no
  cover in range it holds the band and drifts sideways inside it. The
  boosted band and 1 s recalc from Combat Rewards still apply.

`tests/Screenshot.tscn` now also runs a trap-between-enemy-and-knight
scenario and prints whether the enemy avoided it and got past.

## Update, 12 Nov: the playable preview

Everything below still holds, with these changes on top.

**Every stub now has a `# PREVIEW(<owner>)` fill.** A few lines each, under
the GDD constants, so the game can be played end to end: movement, aim,
shooting (`PlayerBullet.gd` is new), HP, grazing through the existing
`GrazeArea`, the Shockwave's effects, kill energy into the meter, barrel and
trap damage, waves, door unlock, walking to a door to advance. They are
deliberately plain. If you own the mechanic, replace the PREVIEW block; the
constants, signals and visual calls around it are the contract.

**The sprites are the reference paintings.** `pipeline/cutout_refs.py` keys
each painting in `docs/reference/` out of its background and writes
game-scale PNGs to `assets/sprites/refs/`. One side view per creature; the
scripts mirror it for left-facing (`flip_h`, only when all 8 frame names
share a texture, so the Blender set is unaffected). `pipeline/make_scenes.py`
has a `SPRITE_SET` switch: `"refs"` (current) or `"blender"`. Sizes are
bigger than the 64 px anchor on purpose; at 64 px the hare's bow vanishes.

**Two painted rooms.** `room_02` is the painted interior, `room_03` the boss
arena (with the boss, bullets and HUD that were painted into that reference
cloned out). Their floors are not the shared rectangle, so `layouts.json`
entries may now carry their own `floor_polygon`, `floor_centre`, `doors`,
`spawn_markers` and `object_markers`; `RoomManager._apply_geometry` applies
them. Rooms without overrides still use the shared framing. `room_01` is
flagged `"standin"` and drawn only after the painted rooms; `room_03` is
flagged `"boss"` and used only for room 8.

**Shadows and life.** Every character and prop has a soft shadow ellipse
(a `GradientTexture2D` the generator writes into each scene), idle
breathing, a walk bob, and a squash on firing. No particles.

**Verification lives in `tests/`.** `tests/Screenshot.tscn` instances
`Main`, drives the knight with fake input through a wave and the boss room,
and saves `build/shots/*.png`. See the README for the three commands.

## How to read a stub

Every script follows the same shape:

```gdscript
## GDD architecture box: what the diagram says this holds
## Reads: which scripts, and for what
## WHAT IS BUILT: ...
## WHAT IS NOT: ...

const GRAZE_DISTANCE_PX: float = 20.0   ## the GDD line it came from

signal meter_changed(value, max_value)  ## already wired to the HUD

func _physics_process(delta):
    # TODO(Daryl): the actual mechanic
    pass
```

Three rules I stuck to, so you can rely on them:

1. **Every GDD number is a named constant.** No magic numbers anywhere. If a
   number is wrong, change it in one place.
2. **Cross-script links are already wired.** Where the GDD says one script
   reads another, the signal connection exists and works. You fill in the
   body, not the plumbing. Example: `Player.took_damage` → `GrazeMeter`
   already subtracts 25.
3. **Visual feedback is already written.** Graze sparks, the Shockwave ring at
   exactly 150 px, the barrel blast ring at exactly 96 px, damage flashes,
   death fades, door lock states, cover damage stages. Call them; don't
   rebuild them.

## The art pipeline

The GDD's pipeline, implemented:

> model and texture in Blender → render with an orthographic camera at a fixed
> 3/4 angle, key light from the top-left → 8-direction sprite sheets → Godot
> AnimatedSprite2D

```bash
./pipeline/render_all.sh          # renders everything, ~10 min
python3 pipeline/check_anchor.py  # measures it against the anchor asset
python3 pipeline/check_gdscript.py  # static check on every .gd
```

`check_gdscript.py` exists because this project's art is built on a machine
with no Godot, so a script that calls a helper nobody wrote survives until
someone opens the editor — and Godot reports only the FIRST parse error, so
those surface one at a time, one round trip each. It catches calls to
undefined private methods, emits of undeclared signals, property setters that
assign to their own property (infinite recursion in Godot 4), mixed
indentation and unbalanced brackets.

| File | What it makes |
|---|---|
| `rig_common.py` | The shared rig. Camera, lights, cel shader, ink outlines, palette. **Everything** goes through this. |
| `player.py` | The anchor asset — the **Nib Knight**. 8 directions. |
| `enemy.py` | The bestiary: Knight Snail, Hare Archer, Grotesque, Ink Scribe. 8 directions each. |
| `room.py` | Renders a room as ONE painted background, and exports its floor outline + markers as pixels into a `.json` beside it, plus the shared `layouts.json` manifest. |
| `props.py` | Lamp Oil, Tome Stack (3 stages), Scribe's Trap (3 states), Pigment Shell, bullets. |
| `extract_palette.py` | Clusters the reference images to measure the palette. |
| `convert_refs.py`, `make_art_bible.py` | Build `docs/ART_BIBLE.pdf`. |
| `props.py` | Bullets, barrel, cover (3 damage stages), trap (armed/disarmed). |
| `tiles.py` | **Retired.** Rooms are painted backgrounds now, not tiles. |
| `check_anchor.py` | Measures any sprite: frame size, content bbox, palette drift. |
| `check_gdscript.py` | Catches parse-level GDScript bugs without opening Godot. **Run it before you push.** |
| `make_scenes.py` | Regenerates `scenes/*.tscn` from the sprites. |

**If you change `rig_common.py`, re-render everything.** A mixed set — half the
assets at one camera angle, half at another — looks worse than an unfinished
one.

### The anchor asset

> The player character's idle sprite, facing down-right, about 64 px tall in a
> 128 × 128 frame. Every other asset is checked against it.

The anchor is now the **Nib Knight** (`docs/reference/hero-nib-knight.png`):
great helm, ember plume, parchment cape, and a spear headed with a fountain-pen
nib charged teal. Exactly two points of colour on him, which is what keeps him
readable against a room full of violet creatures.

Built, and the check is a command rather than an eyeball:

```
$ python3 pipeline/check_anchor.py assets/sprites/player/player_idle_SE.png
  frame      128 x 128
  content    x 47-91  y 9-73   (45 x 65 px)
  height     65 px   target 64 +/- 6
  OK         within anchor tolerance
```

It also reports palette drift, scoring each colour against the swatch ramps
rather than the flat swatches, because cel shading is *supposed* to produce
colours that aren't exactly on a swatch.

## Decisions worth reviewing

These are mine, not the GDD's. Overrule any of them.

**1. The reference beats the GDD on hero proportions.** The avoid list bans
"chibi or cartoon proportions", but the reference knight is deliberately
stocky, and the oversized helm is exactly what makes him read at 64 px. Noted
in `pipeline/player.py` so nobody "fixes" it later by citing the GDD.

**2. Rooms are painted backgrounds, not tilemaps.** The reference room is a
diorama — a floor quadrilateral with three walls around it, ornament on the
walls, floor left plain so bullets read. A 64 px square tile grid can't express
that. `room.py` renders the image *and* exports `room_01.json` with the floor
outline, door anchors and marker positions in pixels, projected through the real
camera. `make_scenes.py` reads that to build collision, so the art and the
engine can't drift apart. The TileSet is deleted.

**3. The room got deeper for a gameplay reason.** At a 45° camera a floor's
on-screen height is `depth × sin(45°)`, so the original 20 m room painted a
964 × 379 px play area — a 2.5:1 strip in which the Shockwave's 150 px radius
covered **79% of the height**, making the GDD's most expensive ability close to
a free room clear. At 28 m it projects to 964 × 530 (1.82:1) and the GDD's
numbers mean what they were balanced to mean.

**4. Species and tier are separate.** `Enemy.gd` has a `species` (snail / hare /
grotesque / scribe) that decides how it looks and behaves, and a `tier()` that
decides HP and kill energy. Adding a second standard-tier creature costs a
sprite sheet and one line, not a balance rewrite.

**5. Enemies share one palette on purpose.** Every creature is violet flesh plus
rust hide — what all three references have in common. Keeping it strict is what
makes a mixed wave read as one family, and as *not* the hero, who is the only
steel-and-teal thing on screen.

**6. `Palette.gd` is new**, holding the measured palette as named constants plus
`check_no_magenta()` — a debug guard that warns if anything except an enemy
bullet is magenta. The GDD calls that "one rule above the rest", so it's
enforced in code rather than in review.

**7. `GameManager` is not literally an autoload.** The diagram says
"Main.tscn, autoload", but a script can't be both in Godot. It lives on
`Main.tscn`'s root and exposes `static var instance`.

## What I did not do

- No mechanic logic. Not movement, not shooting, not waves, not pathing.
- **Nothing has been run in Godot.** There's no Godot binary on the machine I
  built this on. The `.tscn` files are generated to Godot 4 `format=3` and the
  GDScript is written against the 4.x API, but the first person to open the
  project should expect to fix import paths or a node-path typo. That's a
  five-minute job, not a rebuild — but I'd rather flag it than let you find it.
- Only 1 of the 10 room layouts. **See [`ROOM_BRIEF.md`](ROOM_BRIEF.md)** — it
  specifies the exact canvas and floor rectangle every room must hit, plus a
  prompt and a line for each of the ten. Hit the framing and a new room costs a
  PNG and one line in `layouts.json`; collision, doors and spawn markers all
  come from the shared `framing` block.
- **The rooms and props are not final art.** The decided pipeline is hybrid:
  rooms and props as painted/generated 2D (single images, no rotation), characters
  in Blender (8-direction turnarounds are the one thing image generation is bad
  at). What's committed for rooms is a Blender stand-in so the game runs.
- Props still render from the old pre-reference `props.py`. They need rebuilding
  against `docs/reference/props-sheet.png`: Explosive Lamp Oil, Defensive Tome
  Stack, Scribe's Trap, Luminous Pigment Shell.
- No boss model beyond a scaled-up elite with a spike crown. The boss fight is
  due Dec 2.
- No audio, no music, no menus.
